# LangChain: будівельні блоки

## Document
Одиниця тексту в LangChain: `page_content` (сам текст) і `metadata` (словник — звідки взято,
сторінка, автор). Усі лоадери повертають список Document, усі сховища зберігають Document.
Метадані потім можна використати для фільтрації пошуку або щоб показати джерело відповіді.

## Text splitter
LLM має обмежене вікно контексту, а embedding-модель — ще менше. Тому великий файл ріжуть
на чанки. `RecursiveCharacterTextSplitter` пробує різати по абзацах, потім по реченнях,
потім по словах — щоб не рвати думку посеред слова. `chunk_overlap` дає сусіднім чанкам
спільний хвіст, щоб речення на межі не втратило контекст.

## Embeddings
Модель, що перетворює текст у вектор чисел. Близькі за змістом тексти дають близькі вектори,
тому схожість можна рахувати як косинус між ними. Інтерфейс у LangChain мінімальний:
`embed_documents` для списку текстів і `embed_query` для одного питання.
Embeddings — це не LLM: вони не генерують текст, лише вимірюють зміст.

## Vector store
Сховище векторів з пошуком за схожістю. `InMemoryVectorStore` тримає все в пам'яті й зникає
після виходу з процесу — для сотень чанків цього досить. Chroma, Qdrant, pgvector зберігають
індекс на диск і шукають швидко на мільйонах чанків.

## Retriever
Обгортка над сховищем з одним завданням: дістати релевантні Document для запиту.
`store.as_retriever(search_kwargs={"k": 4})` означає «віддай чотири найближчі чанки».
Retriever — повноцінна ланка ланцюжка, тому його можна ставити через `|` як будь-який крок.
Варіанти: MMR-пошук (дає різноманітніші результати), фільтр по метаданих, BM25 без векторів.

## Prompt template
Шаблон з дірками для змінних: `ChatPromptTemplate.from_template("Контекст: {context}")`.
На вході словник зі змінними, на виході — готовий список повідомлень для чат-моделі.

## Chat model
Сама LLM. `ChatOpenAI` говорить протоколом OpenAI, тому підходить і для будь-якого
OpenAI-сумісного шлюзу — достатньо підмінити `base_url`. `temperature=0` робить відповіді
максимально передбачуваними, що для RAG саме те, що треба.

## Output parser
Витягує з відповіді моделі потрібний тип. `StrOutputParser` дає просто текст замість об'єкта
AIMessage. Є парсери в Pydantic-модель, у JSON, у список — тоді LLM стає типізованою функцією.

## LCEL
Спосіб склеювати кроки оператором `|`: `prompt | llm | parser`. Кожна ланка — Runnable,
тому в усіх однаковий набір методів: `invoke` (один вхід), `batch` (багато паралельно),
`stream` (токени по мірі генерації), плюс async-версії. Словник у ланцюжку означає
«порахуй ці гілки й збери результат у словник» — так контекст і питання потрапляють у промпт
за один прохід. Головна вигода: стрімінг і батчинг працюють безкоштовно на всьому ланцюжку.

## RAG
Retrieval-Augmented Generation: замість того щоб сподіватися на пам'ять моделі, спершу шукають
релевантні куски у власних документах і вкладають їх у промпт. Модель відповідає по наданому
контексту, тому менше вигадує і може показати джерело. Якість RAG залежить насамперед від
пошуку: погані чанки — погана відповідь, і жодна LLM цього не виправить.

## Tools і агенти
Tool — звичайна функція з описом, яку модель може викликати сама. Агент — цикл: модель
дивиться на питання, вибирає інструмент, бачить результат, вирішує, чи продовжувати.
У LangChain 1.x агенти живуть у LangGraph (`create_agent`), бо цикл зі станом — це граф,
а не ланцюжок.

## Memory
Ланцюжок за замовчуванням не пам'ятає попередніх реплік: кожен `invoke` незалежний.
Щоб вийшов чат, історію повідомлень тримають окремо й підмішують у промпт — у LangGraph
за це відповідає checkpointer, який зберігає стан діалогу між викликами.
