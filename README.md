# supply-flow — приймання поставки від постачальника

Мережа магазинів отримує поставки щодня. Постачальник перед поставкою скидає накладну
у вільній формі — тілом листа або файлом xlsx. Товарознавець мусить зіставити кожну
позицію з номенклатурою мережі, перевірити ціну проти чинного протоколу погодження цін,
кратність пакування, кількість проти заявки й залишковий термін — і вирішити: приймати,
приймати частково чи відмовити.

Тут це зроблено як граф LangGraph, де LLM відповідає за три речі — перетворити текст у
структуру, зіставити назви з номенклатурою, написати акт розбіжностей — і **не торкається
арифметики**. Чи ціна вища за протокол, чи кількість кратна пакуванню, чи сходиться сума —
рахує код, і це перевіряється тестами без мережі.

Специфікація: [spec.md](specs/001-goods-receipt/spec.md) ·
[plan.md](specs/001-goods-receipt/plan.md) · [tasks.md](specs/001-goods-receipt/tasks.md)

## Запуск

```bash
npm install
npm test                 # 154 тести, офлайн, без API-ключа
npm run seed             # магазини, постачальники, 40 SKU, протоколи, заявки

node supply.mjs intake fixtures/inbox/clean-01-molochka.txt   # чистий документ → проведено
node supply.mjs intake fixtures/inbox/r01-cina-vyshche.txt     # розбіжність → спиняється
node supply.mjs review                                         # черга рішень
node supply.mjs resume <тред> --lines 1,2                      # часткове приймання

npm run web              # те саме у браузері: http://127.0.0.1:5173
npm run eval -- -r 5     # скільки разів зі ста модель читає накладну правильно
```

Додай `--trace` до `intake` чи `resume`, щоб побачити кожен промпт і кожну відповідь
моделі — без цього видно результат вузла, але не його вхід, а причина дивного
результату майже завжди саме там.

## Фронт

`npm run web` підіймає локальну сторінку: вхідні ліворуч, лист і ланцюг у центрі,
таблиця розбіжностей із галочками замість `--lines 1,3`. Збоку видно чергу рішень,
проведені накладні й — найцікавіше — чого система навчилась із твоїх рішень.
Кожен виклик моделі можна розгорнути: промпт і сира відповідь.

Це `node:http` і одна HTML-сторінка, нуль депенденсів і нуль зборки. Слухає тільки
`127.0.0.1`: інструмент для одного стола, а не сервіс. Сторінка-артефакт тут не
підійшла б узагалі — фронту треба дістатись і до твоєї БД, і до шлюзу, а браузер із
`https://` не пустить запит на `http://localhost`.

Ключ до шлюзу opencode береться з `OPENCODE_API_KEY`, інакше з
`~/.local/share/opencode/auth.json`, де його вже тримає opencode CLI.

| Змінна | Дефолт | Нащо |
|---|---|---|
| `SUPPLY_DB` | `./supply.db` | файл БД: бізнес-дані і чекпойнти графа разом |
| `MODEL` | `qwen3.8-flash` | модель шлюзу |
| `OPENCODE_PROVIDER` | `opencode-go` | `opencode` — Zen, pay-as-you-go |

## Потік

```
START → dedupe → extract ⟲ → match → validate ─┬ чисто ────→ commit ─┬→ END
           │       (ретрай ребром,              │                     └→ explain → END
           └→ END   макс 2 спроби)              └ блокуючі → review ⏸ ┤
       (тред уже                                                      └→ explain → END
        закритий)
```

`review` — це справжня пауза: `interrupt()` зберігає стан на диск, а рішення приходить
іншою командою в іншому процесі, можливо через годину. Часткове приймання створює
накладну на схвалені рядки й акт розбіжностей на решту; тред після рішення закривається
і в черзі не лишається.

## Правила приймання

| # | Правило | |
|---|---|---|
| R1 | ціна без ПДВ вища за протокольну (допуск 0 коп.) | блокує |
| R2 | ціна нижча за протокольну | приймаємо, позначаємо |
| R3 | немає чинного протоколу на дату документа | блокує |
| R4 | кількість не кратна пакуванню | блокує |
| R5 | кількість більша за заявлену | блокує |
| R6 | кількість менша за заявлену | приймаємо факт |
| R7 | залишковий термін нижче мінімуму по SKU | блокує |
| R8 | SKU не знайдено або впевненість < 0.8 | блокує |
| R9 | позиції немає в заявці | блокує |
| R10 | сума документа ≠ сумі рядків | блокує |

Порівняння з протоколом завжди ведеться **без ПДВ**, а всі гроші в системі — цілі копійки
(`INTEGER`). Обидва рішення не косметичні: `0.1 + 0.2 !== 0.3` у R1 з нульовим допуском
означає відмову в прийманні на копійку з повітря, а порівняння ціни з ПДВ проти ціни без
нього — найчастіше джерело фальшивого «завищення».

## Чому так, а не простіше

**Шортліст рахує код, вибирає LLM.** Увесь каталог у промпті ламається після ~200 SKU й
дає різні відповіді на однакове питання. Тому кандидати (top-5) добираються детерміновано
за перетином токенів, де токени з цифрами важать удвічі: у молочці саме жирність і
фасування відрізняють сусідні позиції, а слово «молоко» є в десятку назв.

**Аляси.** Коли людина підтвердила, що «Молоко пастеризоване 2,6% 900г п/е» від цього
постачальника — це `MLK-001`, пара (постачальник, нормалізована назва) запам'ятовується.
Наступного разу рядок матчиться без LLM і без людини. Саме це робить таку систему вартою
впровадження: вона дешевіє з кожним листом. Аляс народжується тільки з рішення людини —
аляс із рішення моделі закріпив би галюцинацію назавжди.

Вчиться він і на рядках, які **відкинули через ціну або термін**: зіставлення в них людина
не заперечувала. Не вчиться на двох: `no_sku_match` (під питанням саме збіг) і рядок,
виключений без жодної розбіжності — там причина невідома, і це міг бути неправильний SKU.

**Ідемпотентність у два рівні.** `thread_id = sha256(вмісту)` плюс вузол `dedupe` на вході;
і `UNIQUE(supplier_id, doc_number, doc_date)` на накладній — для випадку, коли той самий
документ прийшов двома каналами й має різні хеші. Перший рівень економить виклики LLM,
другий не дає провести документ двічі.

**`node:sqlite`, а не `better-sqlite3`.** Офіційний чекпойнтер LangGraph залежить від
`better-sqlite3`, але він приймає готовий `db` у конструктор і чіпає лише
`pragma/exec/prepare/transaction` — тому драйвер тут стдлібний, логіка чекпойнтера
офіційна, а між ними шим на двадцять рядків у [db.mjs](src/db.mjs). Нуль нативних
збірок, одне з'єднання на бізнес-дані й чекпойнти.

## Тести

```bash
npm test                      # усе офлайн
npm test -- tests/graph.test.mjs
```

Два рівні: unit на чисту логіку (R1–R10 по одному тесту на правило, нормалізатор назв,
парсер копійок, шортліст, ідемпотентність) і end-to-end на граф, CLI та HTTP-ендпоінти
з моделлю за сценарієм. Моків немає: `buildGraph({ model, db, checkpointer })` і `main(argv, { makeModel, dbFile })`
отримують залежності аргументами, тому `jest.unstable_mockModule` не потрібен ніде.

Модель у тестах — не `FakeListChatModel`, а свій `Scripted`: він падає на несподіваному
виклику, тоді як `FakeListChatModel` крутить список по колу й зайвий виклик моделі пройшов
би непоміченим. А в графі цікава саме кількість викликів — наприклад, у тесті на аляси
модель мусить бути викликана рівно один раз.

PDF і OCR · EDI (Вчасно / EDIN / M.E.Doc) · інтеграція з 1С/BAS · надсилання листів ·
веб-UI · OpenTelemetry / LangSmith · прогін проти справжнього шлюзу в тестах ·
eval-набір із метрикою якості витягу.

якість чужої бібліотеки, а не те, чи працює приймання.
